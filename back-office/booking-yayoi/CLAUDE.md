## 1. プロジェクトの目的

Booking.com 経由の宿泊売上について、**売上発生（チェックアウト）から代金回収（肥後銀行着金）までの一連のサイクル**を管理・記帳する。成果物は2系統。

| 系統 | 成果物 | 用途 |
|---|---|---|
| A. 記帳用 | 弥生会計インポート用 CSV（CP932） | 仕訳の取込 |
| B. 管理用 | 債権管理表（PDF） | 経営報告・回収状況の可視化 |

補助的に Excel ワークブック（突合明細・監査証跡）を作る場合もある。

## 2. 入力データ（3点セット）

毎サイクル、以下3ファイルを揃えることで完全な突合が可能になる。

### 2-1. 送金明細書（Payout レポート）★最重要

- **入手元：** Booking.com YCS ポータル → ファイナンス → 送金明細
- **ファイル名例：** `Payout_from_2026-04-01_until_2026-07-06.csv`
- **形式：** CSV / **UTF-8** / ヘッダー行あり
- **推奨：** PDF版も同時に出せるが、**必ずCSV版を使う**（PDFは日本語が文字化けし抽出精度が落ちる）

**主要カラム：**

| カラム | 内容 |
|---|---|
| `タイプ / 取引タイプ` | `(Payout)` = 送金サマリー行 ／ `予約` = 明細行 |
| `明細書表記` | 送金バッチID（例: `iHTdHWO2WVUVH0Qu`）。同一送金の予約をグルーピングする鍵 |
| `照会番号` | 予約番号（**枝番なし**） |
| `チェックアウト日` | **売上計上月の判定基準**（★後述） |
| `発行日` | Booking側の明細発行日。チェックアウト日とズレる場合あり。**会計には使わない** |
| `予約ステータス` | `OK`（キャンセルは送金明細に載らない） |
| `総額` | グロス売上（コミッション控除前） → **売上計上額** |
| `コミッション` | 12.00%（負数） → **外注費** |
| `決済サービスの手数料` | 2.30%（負数） → **支払手数料** |
| `取引額` | 純額（= 総額 − コミッション − 決済手数料） |
| `お支払い日` | Booking側の送金予定日（通常は翌月1日）。**実着金日ではない** |
| `銀行口座` | `*7458`（肥後銀行と一致することを確認） |

### 2-2. 予約リスト（Reservations エクスポート）

- **入手元：** Booking.com YCS ポータル → 予約 → **出発日（チェックアウト日）でフィルタ**してエクスポート
- **ファイル名例：** `予約_2026-04-01_2026-07-07.xls`
- **形式：** .xls（旧Excel）／ `pandas.read_excel` + `xlrd` で読める
- **カラム：** 宿泊施設名 / ロケーション / 予約者氏名 / Genius会員 / 到着日 / 出発日 / 予約日 / ステータス / 合計料金 / コミッション / 通貨 / 予約番号
- **日付形式：** `2026年5月24日` の和暦風文字列 → 正規表現でパースが必要

**役割：** 予約者氏名の付与、キャンセル分の把握（監査証跡）、送金明細との件数・総額の相互検証。

### 2-3. 肥後銀行 入出金明細 ★実着金日の確定に使う

- **入手元：** 肥後銀行のネットバンキングからダウンロード
- **ファイル名例：** `20260706142843.csv`
- **形式：** CSV / **CP932** / ヘッダーなし・独自レイアウト（1行目が口座情報、2行目以降が明細）
- **Booking入金の抽出条件：** 摘要欄が **`ﾄﾞｲﾂｷﾞﾝｺｳ BOO`**（振込）
- 金額は `\1,430,076` のように円マーク・カンマ付き文字列 → 数値化が必要

**役割：** これがあると入金日をプレースホルダーではなく**実日付で確定**できる。可能な限り毎回セットで用意する。

## 3. 会計処理ルール（確定済み・都度確認不要）

### 3-1. 売上計上（債権の発生）

- **タイミング：** **チェックアウト月の月末**
- **金額：** **総額（グロス／コミッション控除前）**

| 借方 | 貸方 | 税区分 |
|---|---|---|
| 売掛金（補助科目: Booking.com）／ 総額 | 売上高 ／ 総額 | **課税売上込10%（内税）** |

### 3-2. 入金消込（債権の回収）

- **タイミング：** 翌月の**肥後銀行 実着金日**
- **形式：** **諸口による複合仕訳**（借方3行 vs 貸方1行、貸借ゼロ balance）
- **伝票番号：** 消込行は同一伝票番号でグルーピングする

| 借方 | 金額 | 税区分 |
|---|---|---|
| 普通預金（補助科目: 肥後銀行） | 純額（取引額） | — |
| 外注費 | コミッション（12%） | **対象外（不課税・国外）** |
| 支払手数料 | 決済サービスの手数料（2.3%） | **対象外（不課税・国外）** |

| 貸方 | 金額 |
|---|---|
| 売掛金（補助科目: Booking.com） | 総額 |

→ 消込後の売掛金残高は **ゼロ** になること。これが検証条件。

### 3-3. キャンセル

キャンセル済み予約は送金明細に載らないため、**仕訳は不要**。ただし Excel / 管理表には監査証跡として残す。

## 4. データ処理の注意点（ハマりどころ）

### ★ 4-1. 予約リストの「コミッション」列は会計に使えない

予約リストのコミッション列は **12%（コミッション）＋ 2.3%（決済手数料）＝ 14.3% の合算値**であり、かつ**小数（端数未処理）**。

```
例）予約 6185753465：総額 182,600
    予約リストのコミッション列 = 26,111.8
    送金明細              = コミッション 21,912 + 決済手数料 4,200 = 26,112
```

→ **外注費と支払手数料への分解は送金明細からしか取れない。** 予約リストの数値をそのまま記帳に使わないこと。

### ★ 4-2. 計上月は「チェックアウト日」で判定する

- 送金明細の `発行日` はチェックアウト日とズレることがある（例: 予約 6265702719 は CO 5/24・発行日 5/25）。
- 月をまたぐ滞在（例: 予約 5790277292 は IN 5/30 → OUT 6/4）は、**チェックアウト日基準で6月計上**。
- **必ず `チェックアウト日` を使う。** `発行日` `お支払い日` は使わない。

### 4-3. 送金明細の金額を最優先する（優先順位ルール）

予約リストと送金明細で金額が食い違った場合、**送金明細を正とする**。
（過去に1件、¥1の丸め差異が発生した際に確立したルール）

### 4-4. iPass エクスポートを使う場合

Booking.com の予約リストではなく iPass 側のエクスポートを使うケースでは、以下の癖に注意。

- 予約番号に **枝番サフィックス（`_01` 等）** が付く → 照合前に除去する
- 明細行が**泊数・室数で分割**されており、月をまたぐ予約で按分がズレる → **売上計上には行単位の合計ではなく送金明細のグロス総額を使う**

### 4-5. エンコーディング一覧

| ファイル | エンコーディング |
|---|---|
| 送金明細 CSV | UTF-8 |
| 肥後銀行明細 CSV | **CP932** |
| **弥生インポート CSV（出力）** | **CP932** |

## 5. 弥生会計インポートCSV 仕様

- **エンコーディング：CP932**
- **ヘッダー行：なし**
- **形式：複合仕訳（諸口方式）**
- **補助科目名は弥生のマスタ登録と完全一致させる**（`Booking.com` / `肥後銀行`）。不一致はインポートエラーの原因になる。
- 勘定科目名・税区分名も同様にマスタ表記と一致必須。

**入金日について：** 肥後銀行明細が手元にある場合は実着金日を入れる。無い場合はプレースホルダー（送金明細の「お支払い日」等）を入れ、**取込前に実際の着金日へ差し替える**旨を必ず申し送る。

## 6. 債権管理表（PDF）仕様

- **サイズ：** A4 横（landscape）
- **フォント：** 日本語TTF必須。`/usr/share/fonts/truetype/fonts-japanese-gothic.ttf` を使用
  （Noto CJK の `.ttc` は PostScript outline のため ReportLab で読めない）
- **ライブラリ：** ReportLab（Platypus）

**構成：**

1. **回収サイクル サマリー** — チェックアウト月 × [件数 / ①総額 / ②コミッション / ③決済手数料 / ④純額 / 計上日 / 送金明細日 / 実入金日 / 実入金額 / 消込判定]
2. **会計処理の考え方** — 売上計上・入金消込の仕訳表
3. **要確認事項のフラグボックス** — 未解明の差異・対象範囲外の期間
4. **月別明細（予約単位）** — 予約番号 / 予約者名 / CO日 / 総額 / コミッション / 決済手数料 / 純額 / 状態、小計と消込結果

**視覚ルール：**
- 消込一致 → 緑字・「○」
- 未解明の差異がある月 → **オレンジ枠**で仮フラグ（具体的な差異が特定できなくても、省略せず「要確認（仮）」として可視化する。実務上の使いやすさを、見せかけの精緻さより優先する）

## 7. 標準ワークフロー（毎サイクル）

1. **データ受領** — 送金明細CSV + 予約リスト（出発日フィルタ） + 肥後銀行明細
2. **突合（4階層すべて検証）**
   - 送金明細の明細行合計 = `(Payout)` サマリー行の金額
   - 予約リスト（ステータス OK）の総額 = 送金明細の総額
   - 予約番号ベースで全件マッチ（漏れ・余剰ゼロ）
   - **送金明細の純額 = 肥後銀行の実入金額**
3. **仕訳生成** — 売上計上（CO月末）＋ 入金消込（実着金日・諸口）
4. **成果物出力** — 弥生CSV（CP932）／債権管理表PDF／（必要に応じ）Excel
5. **申し送り** — 入金日プレースホルダーの有無、差異フラグ、補助科目名の一致確認

## 10. 技術メモ（再現用）

- 処理言語：Python / pandas
- 必要パッケージ：`pandas`, `xlrd`（.xls読込）, `reportlab`（PDF生成）, `pdf2image`（出力検証）
- 予約リストの日付パース：`re.match(r'(\d+)年(\d+)月(\d+)日', s)`
- 肥後銀行明細の金額パース：`\` とカンマを除去して int 化
- PDF生成後は画像化して目視確認する（文字化け・レイアウト崩れの検出）
